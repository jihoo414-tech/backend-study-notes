# HTTP 멱등성

## 한눈에 보기

HTTP 메서드가 멱등하다는 것은 **동일한 요청을 여러 번 보냈을 때 서버에 의도된 효과가 한 번 보낸 것과 같음**을 뜻한다. 응답 본문이나 상태 코드가 매번 완전히 같아야 한다는 뜻은 아니다.

예를 들어 같은 리소스를 삭제하는 `DELETE` 요청을 반복하면 첫 응답은 `204 No Content`, 다음 응답은 `404 Not Found`일 수 있다. 응답은 달라도 리소스가 삭제된 서버 상태는 같으므로 멱등성을 만족할 수 있다.

## 왜 필요한가

네트워크 오류로 응답을 받지 못하면 클라이언트나 중간 시스템이 요청을 재시도할 수 있다. 멱등한 작업은 같은 요청이 중복 전달되어도 의도하지 않은 추가 변경을 만들지 않으므로 재시도를 더 안전하게 설계할 수 있다.

## 핵심 개념

| HTTP 메서드 | 명세상 멱등성 | 핵심 의미 |
| --- | --- | --- |
| `GET` | 멱등 | 리소스를 조회한다. 동일 요청을 반복해도 요청 자체가 서버 상태를 변경하도록 의도되지 않는다. |
| `PUT` | 멱등 | 대상 리소스의 상태를 요청 표현으로 생성하거나 교체한다. 같은 표현을 반복 적용한 최종 상태는 같다. |
| `DELETE` | 멱등 | 대상 리소스를 제거한다. 이미 제거된 뒤 다시 요청해도 의도된 최종 상태는 같다. |
| `POST` | 멱등 보장 없음 | 같은 요청마다 새 리소스 생성이나 결제 같은 추가 효과가 생길 수 있다. |
| `PATCH` | 멱등 보장 없음 | 부분 변경 방식에 따라 반복 적용 결과가 달라질 수 있다. 구현에 따라 멱등하게 만들 수는 있다. |

`GET` 응답은 데이터 변경, 시간 경과, 권한 상태 등에 따라 달라질 수 있다. 이 변화 때문에 `GET`의 멱등성이 사라지는 것은 아니다. 멱등성은 **반복 요청이 서버에 만드는 의도된 효과**를 기준으로 판단한다.

## 동작 원리

```text
동일한 요청 1회  → 서버의 최종 상태 S
동일한 요청 N회 → 서버의 최종 상태 S
```

위 관계가 성립하면 해당 연산은 멱등하다고 볼 수 있다. 로그 기록, 통계 수집처럼 요청 처리에 따라 생기는 부수 효과까지 반드시 동일해야 한다는 의미는 아니다.

## 예제

```http
PUT /members/1
Content-Type: application/json

{"name":"kim"}
```

같은 요청을 여러 번 보내도 회원 1의 이름을 `kim`으로 만드는 최종 결과는 같다.

```http
POST /orders
Content-Type: application/json

{"productId":10,"quantity":1}
```

서버가 매번 새 주문을 생성한다면 같은 요청을 두 번 보냈을 때 주문도 두 개 생길 수 있으므로 멱등하지 않다. 필요하다면 클라이언트가 보낸 고유 요청 식별자를 저장하고 중복 요청에 이전 처리 결과를 연결하는 방식 등을 별도로 설계해야 한다.

## 주의사항

- HTTP 메서드의 명세상 성질과 실제 서버 구현은 구분한다. `GET` 요청에서 데이터를 변경하도록 구현하면 HTTP 의미를 어긴 것이다.
- `POST`가 언제나 멱등하지 않아야 한다는 뜻은 아니다. 명세가 멱등성을 보장하지 않을 뿐, 애플리케이션이 중복 방지 정책을 구현할 수 있다.
- 메모리나 DB 상태를 변경하는지 여부만으로 판단하지 않는다. 같은 값으로 교체하는 `PUT`도 상태를 변경하지만 멱등할 수 있다.
- 멱등성과 안전성은 다르다. 안전한 메서드는 읽기 전용 의미를 가지며, 멱등한 `PUT`과 `DELETE`는 서버 상태를 바꿀 수 있다.

## 관련 개념

- HTTP 메서드의 안전성
- 네트워크 재시도와 중복 요청
- 중복 결제·중복 주문 방지
