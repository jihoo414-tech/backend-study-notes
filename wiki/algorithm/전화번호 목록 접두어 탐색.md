# 전화번호 목록 접두어 탐색

## 한눈에 보기

핵심은 `HashMap`을 갑자기 떠올리는 것이 아니라 비교 대상을 바꾸는 것이다.

```text
모든 전화번호 쌍 비교
→ 현재 번호에서 만들 수 있는 접두어만 생성
→ 그 접두어가 전화번호부에 있는지 해시로 조회
```

전화번호 수 `N`은 최대 1,000,000이지만 전화번호 길이 `L`은 최대 20이다. 큰 축인 다른 전화번호 전체를 내부 반복문에서 순회하지 않고, 작은 축인 현재 번호의 길이를 순회하는 것이 핵심 개선이다.

## 처음 풀이와 실패 원인

사용자의 풀이는 `i < j`인 모든 번호 쌍을 한 번씩 고르고 양방향으로 `startsWith()`를 검사한다.

```java
for (int i = 0; i < phoneBook.length - 1; i++) {
    for (int j = i + 1; j < phoneBook.length; j++) {
        if (phoneBook[i].startsWith(phoneBook[j])) return false;
        if (phoneBook[j].startsWith(phoneBook[i])) return false;
    }
}
```

논리는 맞지만 약 `N(N-1)/2`개의 쌍을 비교하고 문자열 비교에도 최대 `L`이 필요해 `O(N²L)`이다. 실제 제출 결과는 정확성 83.3점, 효율성 8.3점, 합계 91.7점이었다. 즉 틀린 아이디어라기보다 입력 크기를 감당하지 못한 방법이다.

## 발상을 만드는 과정

### 1. 질문을 뒤집는다

`이 번호와 접두어 관계인 다른 번호를 모두 찾자`라고 생각하면 다른 번호를 전부 비교하게 된다. 대신 다음처럼 질문한다.

> 현재 번호가 가질 수 있는 접두어 중 전화번호부에 등록된 것이 있는가?

예를 들어 `1195524421`의 더 짧은 접두어는 길이마다 하나뿐이다.

```text
1, 11, 119, 1195, ..., 119552442
```

이 후보 중 `119`가 등록되어 있는지 빠르게 확인하면 된다.

### 2. 필요한 연산을 찾는다

필요한 연산은 문자열의 순회나 인덱스 조회가 아니라 `이 문자열이 등록되어 있는가?`라는 존재 확인이다. 모든 전화번호를 해시 기반 구조에 먼저 저장하면 각 접두어를 평균적으로 빠르게 조회할 수 있다.

### 3. 내부 반복문의 축을 바꾼다

- 완전 탐색: 번호 하나마다 다른 `N`개를 확인한다.
- 개선 탐색: 번호 하나마다 길이 `L` 이하의 접두어만 확인한다.

이것이 `N²`을 제거하는 실제 발상이다. 코드를 외우기보다 `다른 입력 열거`를 `현재 입력에서 후보 생성`으로 바꾸는 연습을 해야 한다.

## HashMap 풀이

```java
import java.util.HashMap;
import java.util.Map;

class Solution {
    public boolean solution(String[] phoneBook) {
        Map<String, Integer> map = new HashMap<>();

        for (int i = 0; i < phoneBook.length; i++) {
            map.put(phoneBook[i], i);
        }

        for (String phoneNumber : phoneBook) {
            for (int end = 1; end < phoneNumber.length(); end++) {
                String prefix = phoneNumber.substring(0, end);
                if (map.containsKey(prefix)) {
                    return false;
                }
            }
        }
        return true;
    }
}
```

`end = 1`은 빈 문자열을 제외한다. `end < phoneNumber.length()`는 번호 전체, 즉 자기 자신을 후보에서 제외한다. 비교 코드의 인덱스 값은 이후 사용하지 않으므로 존재 여부만 필요하다는 관점에서는 `HashSet<String>`이 의도를 더 직접적으로 표현한다.

## HashSet으로 표현한 풀이

```java
import java.util.Arrays;
import java.util.HashSet;
import java.util.Set;

class Solution {
    public boolean solution(String[] phoneBook) {
        Set<String> numbers = new HashSet<>(Arrays.asList(phoneBook));

        for (String phoneNumber : phoneBook) {
            for (int end = 1; end < phoneNumber.length(); end++) {
                if (numbers.contains(phoneNumber.substring(0, end))) {
                    return false;
                }
            }
        }
        return true;
    }
}
```

## 시간 복잡도

해시 조회를 평균 `O(1)`로 단순화하면 흔히 `O(NL)`로 설명한다. 다만 Java에서 `substring()`으로 새 문자열을 만들고 그 문자열의 해시를 계산하는 비용까지 포함하면 길이 1부터 `L-1`까지의 합이 생기므로 엄밀한 상한은 `O(NL²)`로 볼 수 있다.

```text
번호 하나: 1 + 2 + ... + (L - 1) = O(L²)
전체: O(NL²)
```

이 문제에서는 `L ≤ 20`이므로 중요한 개선은 `N²`을 제거한 것이다. 추가 공간은 해시 엔트리 기준 `O(N)`, 문자열 총길이를 일반화하면 `O(NL)`이다.

## 정렬 풀이와 비교

해시 풀이만이 유일한 이상적 풀이는 아니다. 전화번호를 사전순으로 정렬하면 접두어 관계인 두 번호가 이웃하게 되므로 인접 항목만 비교할 수 있다.

```java
import java.util.Arrays;

class Solution {
    public boolean solution(String[] phoneBook) {
        Arrays.sort(phoneBook);
        for (int i = 0; i < phoneBook.length - 1; i++) {
            if (phoneBook[i + 1].startsWith(phoneBook[i])) return false;
        }
        return true;
    }
}
```

문자열 비교 비용을 포함하면 대략 `O(N log N × L)`이다. 접두어 생성 방식이 아직 직관적이지 않다면 정렬 후 인접 비교가 더 이해하기 쉬운 대안이다.

## 연습 방법

다시 풀 때는 다음 질문을 코드보다 먼저 적는다.

1. 완전 탐색은 정확히 무엇을 전부 비교하는가?
2. 원하는 관계의 후보를 현재 데이터에서 직접 만들 수 있는가?
3. 입력 제한에서 `N`과 `L` 중 어느 축이 작은가?
4. 후보의 존재 여부를 어떤 자료구조로 빠르게 확인할 수 있는가?

외울 문장은 하나면 충분하다.

> 다른 번호를 전부 보지 말고, 현재 번호의 접두어를 만들어 해시에서 찾는다.

## 주의사항

- `HashMap.containsKey()`의 평균 `O(1)`만 보고 문자열 생성과 해시 계산 비용을 무시하지 않는다.
- 값인 인덱스를 사용하지 않으므로 `Map<String, Integer>`만이 정답은 아니다.
- 전체 전화번호까지 접두어 후보로 검사하면 자기 자신 때문에 항상 `false`가 된다.
- 개선 풀이의 실제 통과 여부는 아직 사용자의 재제출로 확인되지 않았다.
