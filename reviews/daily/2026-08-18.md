# 2026-08-18 일일 학습 리뷰

## 오늘 달라진 점

- 고정된 Spring Boot 템플릿을 유지하면서 Todo API의 생성·조회·목록·완료 처리 요구사항을 구현했다.
- 처음 사용한 Java `record`, 요청·응답 DTO, 전역 예외 처리 구조가 실제 API 계층에서 어떤 역할을 하는지 경험했다.
- 전화번호 목록의 완전 탐색이 논리적으로는 맞지만 최대 1,000,000개 입력에서 `O(N²L)`을 감당하지 못함을 제출 결과로 확인했다.
- 비교 대상을 모든 전화번호 쌍에서 각 번호가 가질 수 있는 접두어로 바꾸는 관점을 학습했다.

## 새로 설명할 수 있게 된 것

- Controller가 HTTP 요청과 응답 변환을 담당하고, Service가 입력 검증과 상태 충돌 같은 비즈니스 규칙을 처리하며, Repository가 메모리 저장을 담당하는 책임 구분
- Entity를 직접 반환하지 않고 `TodoResponse`와 `CompleteTodoResponse`로 공개할 응답 형태를 제한하는 이유
- `ApiException`의 상태·코드·메시지를 `GlobalExceptionHandler`가 일관된 `ErrorResponse` JSON으로 변환하는 흐름
- ID 조회와 등록 순서 반환을 함께 만족시키기 위해 `LinkedHashMap`을 사용하는 이유
- 모든 번호를 해시 구조에 저장한 뒤 긴 번호의 접두어가 등록되어 있는지 확인하는 흐름
- `Map<String, Integer>`의 값이 사용되지 않으므로 `HashSet<String>`도 적합하다는 점
- 사전순 정렬 후 인접한 문자열만 비교하는 대안

## 직접 구현하거나 검증한 것

- `POST /todos`, `GET /todos/{id}`, `GET /todos`, `PATCH /todos/{id}/complete` 흐름을 구현했다.
- null·blank·100자 초과 title은 400, 없는 Todo는 404, 이미 완료된 Todo는 409가 되도록 Service 규칙을 구현했다.
- Todo와 요청·응답·오류 데이터 객체에 Java `record`가 사용된 구현을 확인했다.
- 날짜 정정 처리 과정에서 로컬 `gradlew.bat test`를 다시 실행해 저장소에 포함된 공개 테스트 2개가 `BUILD SUCCESSFUL`로 통과함을 확인했다.
- 이중 반복문과 `startsWith()`를 사용한 전화번호 목록 완전 탐색 풀이를 작성하고 제출했다.
- 전화번호 목록 제출 결과는 정확성 83.3점, 효율성 8.3점, 합계 91.7점이었다.
- 해시 개선 풀이는 제공받았지만 사용자의 재제출 성공 여부는 아직 확인하지 않았다.
- 쉬운코드 시간 복잡도 영상을 시청했다. Big-O·Big-Omega·Theta 등의 표기와 best·worst·average case가 있다는 수준으로 확인했으며, 별도 심화 개념으로 확장하지 않았다.

## 기존 지식과의 연결

- [List와 Map 선택 기준](../../wiki/java/List%EC%99%80%20Map%20%EC%84%A0%ED%83%9D%20%EA%B8%B0%EC%A4%80.md)에 ID 조회와 삽입 순서 보존을 함께 요구한 mission-07의 `LinkedHashMap` 적용을 연결했다.
- [Spring Bean Validation](../../wiki/spring/Spring%20Bean%20Validation.md)과 비교하면 이번 구현은 애너테이션 기반 검증이 아니라 Service에서 title 규칙을 수동 검사하고 `ApiException`을 던지는 방식이다.
- [HTTP 멱등성](../../wiki/cs/network/HTTP%20%EB%A9%B1%EB%93%B1%EC%84%B1.md) 관점에서 완료 API는 첫 요청은 성공하고 재요청은 409가 되지만, 첫 완료 이후 서버의 Todo 상태는 계속 `completed=true`로 유지된다.
- [List와 Map 선택 기준](../../wiki/java/List%EC%99%80%20Map%20%EC%84%A0%ED%83%9D%20%EA%B8%B0%EC%A4%80.md)의 주요 연산 중심 자료구조 선택을 전화번호 문자열의 존재 확인에도 적용했다.
- [문자열 순회와 변환 패턴](../../wiki/algorithm/%EB%AC%B8%EC%9E%90%EC%97%B4%20%EC%88%9C%ED%9A%8C%EC%99%80%20%EB%B3%80%ED%99%98%20%ED%8C%A8%ED%84%B4.md)의 부분 문자열 순회와 접두어 생성을 연결했다.

## 아직 설명하거나 검증하지 못한 것

- 저장소의 공개 테스트 코드는 blank title과 생성 후 단건 조회 두 사례만 포함하므로, `TEST_SPEC.md`의 전체 공개 범위와 hidden test는 직접 검증하지 못했다.
- 동시 요청에서 `LinkedHashMap` 접근이 안전한지는 요구사항과 테스트 범위에서 확인되지 않았다.
- 사용자는 Java라고 기록했으며, 로컬 빌드 설정에서는 Java 25와 Spring Boot 4.0.2를 사용한다.
- 전화번호 목록 개선 풀이의 프로그래머스 전체 테스트 통과 여부와 실패한 정확한 테스트 번호는 확인하지 못했다.
- 전화번호 목록 풀이에 사용한 Java 세부 버전은 제공되지 않았다.

## 후속 학습 연결
